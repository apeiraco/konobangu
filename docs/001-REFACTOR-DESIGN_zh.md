# 001-重构设计

## 状态

草稿

## 目标受众

- 从事后端、数据库和 GraphQL 层开发的开发者
- 执行代码迁移、重构和审查任务的 AI 代理

## 目的

本文档定义了从当前基于 `seaography-1.x.x` 分叉的授权模型迁移到以 PostgreSQL 行级安全（RLS）为中心的设计的计划，GraphQL/应用层仅保留有限且可替换的授权逻辑。

本次重构旨在实现以下目标：

- 消除对私有 Seaography 分叉进行用户级授权的长期依赖
- 使数据隔离在 PostgreSQL 层可强制执行
- 保持 GraphQL 授权逻辑简洁、局部化且框架可替换
- 在实际可行的情况下保留 schema/实体反射的生产力优势
- 减少嵌入在框架内部机制中的隐藏授权行为
- 产生可经受框架或语言替换的迁移路径

---

## 背景

现有系统通过分叉并修补 `seaography-1.x.x` 来实现用户权限控制。

这种方法解决了短期需求，但带来了几个结构性问题：

- 授权行为部分隐藏在框架分叉中
- 升级成本高，因为安全逻辑与上游框架内部机制纠缠在一起
- 授权语义无法移植到其他 GraphQL 框架或其他语言
- 正确性依赖于应用层行为而非数据库强制执行的规则
- 未来非 GraphQL 入口点可能会意外绕过当前保护模型

对于本项目，用户拥有的资源（如订阅、下载任务和观看进度）绝不能泄露给其他用户。这一要求不应依赖于 Seaography 特定内部机制的持续存在。

因此，目标设计如下：

- **PostgreSQL RLS 是行级数据隔离的事实来源**
- **GraphQL 层授权是次要的优化和用户体验层**
- **Seaography 特定的 RBAC 不作为核心架构依赖使用**
- **Seaography 守卫和过滤器仅以有限且可替换的方式使用**

---

## 非目标

本次重构**不**尝试：

- 重新设计整个领域模型
- 用 REST 或其他协议替换 GraphQL
- 消除 Seaography
- 创建一个通用的企业 RBAC 系统
- 预先解决所有未来的多租户或共享场景
- 在安全正确性确立之前优化每个查询

---

## 设计原则

### 1. 数据库强制执行所有权优于框架强制执行所有权

如果某行是用户私有的，数据库必须强制执行可见性和可变性限制。

### 2. 授权逻辑应该清晰可读

开发者和 AI 代理应该能够识别访问控制所在位置：

- 行所有权和行可见性：PostgreSQL 策略
- 端点/变更准入：应用或 GraphQL 守卫
- 查询便捷过滤：GraphQL 过滤器或解析器组合

### 3. 优先使用可移植的授权语义

我们应该支持可以重新表达为以下形式的设计：

- 另一个 GraphQL 框架
- 另一个 Rust 技术栈
- 另一种语言
- 未来 REST 或任务处理入口点

### 4. 避免生成代码中隐藏的安全魔法

生成的 schema 暴露是有用的。但代码生成或分叉内部机制中隐藏的安全假设则不是。

### 5. 优先使用明确的所有权列

私有表通常应该有直接的 `subscriber_id` 列，而不是通过复杂连接依赖间接所有权推断。

## 目标架构

### 授权分层

重构后的系统使用具有不同职责的三层。

#### A 层：PostgreSQL RLS（强制，权威）

负责：

- 用户可以 `SELECT` 哪些行
- 用户可以 `UPDATE` 哪些行
- 用户可以 `DELETE` 哪些行
- 用户可以 `INSERT` 哪些行
- 防止任何后端路径中意外发生跨用户数据泄露

这是硬安全边界。

#### B 层：应用请求上下文（强制）

负责：

- 对调用者进行身份验证
- 派生 `subscriber_id`、角色和认证状态
- 将当前用户身份绑定到数据库会话/事务上下文
- 将认证上下文传递给 GraphQL 解析器

该层将身份连接到数据库和 API 表面。

#### C 层：GraphQL 守卫/过滤器钩子（可选但推荐）

负责：

- 尽早拒绝未认证访问
- 简化常见查询约束
- 提供更清晰的 API 行为和错误响应
- 在生成的 GraphQL API 中保留人体工程学

这是便捷和 API 塑形层，不是根本安全层。

---

## 为什么不用 Seaography RBAC 作为基础

Seaography RBAC 在某些项目中可能有用，但不应被视为本次迁移的核心。

原因：

- 它增加了与 Seaography 和 SeaORM 内部机制的耦合
- 使未来框架替换成本更高
- 可能会以不同形式重现当前问题
- 行级所有权在 PostgreSQL 中直接表达比在框架特定的授权抽象中更好

决定：

- **不要**围绕 Seaography RBAC 构建新的权限系统
- **不要**要求 Seaography RBAC 来保证正确性
- **不要**仅在框架级 RBAC 中编码核心行所有权保证

允许的用法：

- 未来团队可以将 Seaography RBAC 评估用于非关键便捷场景
- 任何此类采用必须是附加的，且不得取代 RLS 支持的保证

## 资源分类

迁移应首先将表分类为访问类别。

### 类别 1：用户私有表

示例：

- `subscription`（订阅）
- `download_task`（下载任务）
- `watch_progress`（观看进度）
- `notification_rule`（通知规则）
- `user_feed_preference`（用户订阅源偏好）
- `download_profile`（如果是用户范围的）

规则：

- 必须包含直接所有权信息，通常是 `subscriber_id`
- 必须受 RLS 保护
- GraphQL 访问应默认假设为当前用户范围

### 类别 2：共享或全局引用表

示例：

- `anime`（动漫）
- `episode`（集）
- `subtitle_group`（字幕组）
- 元数据缓存或规范化目录表

规则：

- 通常不需要按用户的 RLS
- 变更（如果有）应受管理员/操作员规则限制
- 读取访问可能是公开的或需要认证，取决于产品设计

### 类别 3：混合范围表

示例：

- 共享收藏
- 协作观看列表
- 具有按用户可见性元数据的系统生成推荐

规则：

- 除非当前需要，否则推迟高级共享设计
- 不要过早过度泛化
- 在通过生成 API 公开之前明确编码所有权和访问语义

---

## 规范安全模型

### 所有权模型

对于用户私有行：

- 每行明确属于一个用户，除非另有明确设计
- 所有权由直接列表示，通常是 `subscriber_id`
- 认证用户只能访问 `row.subscriber_id == current_subscriber_id` 的行

### 变更模型

对于用户私有行：

- 创建：行必须在当前认证用户下创建
- 更新：只能更新当前认证用户拥有的行
- 删除：只能删除当前认证用户拥有的行

### 字段事实来源

对于所有权字段（如 `subscriber_id`）：

- 服务器应从认证上下文派生它们
- 客户端提供的数据应在普通用户流程中被忽略或拒绝

---

## 数据库设计要求

### 1. 添加明确的所有权列

每个用户私有表必须有直接的所有权列，除非有非常强的理由不这样做。

首选形式：

```sql
subscriber_id uuid not null references app_user(id)
```

避免只能通过深度连接推断所有权的模式，例如：

- `download_task -> subscription -> profile -> user`
- `watch_progress -> episode_state -> library -> user`

这些模式使 RLS 更难推理和审计。

### 2. 在私有表上启用 RLS

对于每个用户私有表：

```sql
ALTER TABLE subscription ENABLE ROW LEVEL SECURITY;
ALTER TABLE subscription FORCE ROW LEVEL SECURITY;
```

推荐使用 `FORCE ROW LEVEL SECURITY`，这样表所有权在使用过程中不会静默绕过策略。

### 3. 定义明确的策略

典型策略结构：

- 使用当前会话用户的 `SELECT` 策略
- 检查插入行所有权的 `INSERT` 策略
- 限制旧行资格和新行有效性的 `UPDATE` 策略
- 限制可删除行的 `DELETE` 策略

概念模式：

```sql
CREATE POLICY subscription_select ON subscription
FOR SELECT
USING (subscriber_id = current_setting('app.subscriber_id', true)::uuid);

CREATE POLICY subscription_insert ON subscription
FOR INSERT
WITH CHECK (subscriber_id = current_setting('app.subscriber_id', true)::uuid);

CREATE POLICY subscription_update ON subscription
FOR UPDATE
USING (subscriber_id = current_setting('app.subscriber_id', true)::uuid)
WITH CHECK (subscriber_id = current_setting('app.subscriber_id', true)::uuid);

CREATE POLICY subscription_delete ON subscription
FOR DELETE
USING (subscriber_id = current_setting('app.subscriber_id', true)::uuid);
```

### 4. 运行时 DB 角色不得绕过 RLS

应用运行时连接不得使用绕过 RLS 语义的角色。

分离关注点：

- 迁移角色：允许提升权限
- 运行时角色：受限，受 RLS 约束

### 5. 当前用户必须绑定到 DB 会话或事务范围

每个认证请求必须在 DB 可见的方式中建立当前应用用户身份。

推荐模式：

```sql
SET LOCAL app.subscriber_id = '<authenticated-user-uuid>';
```

这应该在执行用户范围查询之前，在请求事务或请求绑定连接上下文内发生。

## GraphQL 层设计

### 重构后 GraphQL 的作用

GraphQL 不再负责行级数据隔离的最终正确性。

相反，GraphQL 应该：

- 提供对生成 schema 的人机工程学访问
- 尽早拒绝明显无效的访问
- 减少对客户端的意外行为
- 表达不值得推入 SQL 策略的应用级语义

### 允许的 Seaography 用法

允许和推荐：

- 用于认证和粗粒度路由准入的浅层守卫
- 附加用户范围条件以提高清晰度和 API 人机工程学的过滤器或生命周期钩子
- 所有权必须从服务器派生的有限自定义解析器或变更

不推荐作为基础：

- 深度框架特定的 RBAC 纠缠
- 再次硬分叉 Seaography 以恢复安全关键行为
- 依赖允许客户端直接控制所有权列的生成 CRUD 变更

---

## 守卫和过滤器指导

### 守卫

将守卫用于粗粒度访问检查，例如：

- 用户必须已认证
- 仅管理员变更
- 匿名调用者无法使用功能

守卫应该回答这样的问题：

- 这个请求是否可以进入此操作？

守卫**不应**是防止跨用户数据访问的唯一机制。

### 过滤器

将过滤器用于 API 便捷性，例如自动将用户私有实体限制为当前用户范围。

示例：

- 查询 `Subscription` 时，在 GraphQL 中自动限定为当前用户
- 列出 `DownloadTask` 时，预应用当前用户条件

过滤器很有用，因为它们：

- 减少意外的大范围查询
- 改善 API 人机工程学
- 使生成的 GraphQL 端点行为更直观

但过滤器仍然是 RLS 的辅助。

---

## 自定义变更指导

生成的 CRUD 变更对于用户拥有的实体通常过于宽松。

对于用户私有表，在以下情况下优先使用自定义变更：

- 所有权必须从认证上下文派生
- 某些字段对用户必须是不可变的
- 创建/更新流程需要领域验证
- 批量操作需要仔细控制的语义

示例：

- `createSubscription(animeId, ruleInput, profileId)`
- `pauseDownloadTask(taskId)`
- `removeSubscription(subscriptionId)`

避免用户可以自由提交或修改以下内容的通用模式：

- `subscriber_id`
- 所有者引用
- 内部状态字段
- 仅管理员元数据

## 迁移策略

迁移应该是增量的，而不是一次性重写。

### 阶段 0：发现和盘点

创建当前授权行为的详细清单。

任务：

- 识别 Seaography 分叉中实现的所有授权逻辑
- 将每个行为映射到以下目标之一：
  - RLS 策略
  - GraphQL 守卫
  - GraphQL 过滤器
  - 自定义解析器或变更
  - 要移除的过时行为
- 按访问类别对所有表进行分类
- 识别缺少明确 `subscriber_id` 的表
- 识别当前暴露所有权敏感字段的所有生成变更

交付物：

- 授权行为清单
- 表分类矩阵
- 迁移风险列表

### 阶段 1：Schema 准备

任务：

- 在缺少的地方添加 `subscriber_id` 列
- 回填所有权数据
- 添加用户范围查询所需的索引，通常包括 `(subscriber_id, id)` 或 `(subscriber_id, foreign_key)`
- 清理所有权不明确的行
- 为私有表定义不变量

退出标准：

- 每个用户私有表都有明确的所有权语义
- 遗留所有权模糊性已消除或明确推迟

### 阶段 2：引入 RLS 阴影模式

任务：

- 为用户私有表编写 RLS 策略
- 添加设置 `app.subscriber_id` 的请求逻辑
- 添加验证 DB 级别隔离的集成测试
- 暂时保持现有应用层授权活动

推荐推出方式：

- 首先在开发和测试中启用 RLS
- 使用集成测试和手动跨用户场景进行验证
- 与遗留分叉授权行为进行比较

退出标准：

- DB 级别测试证明跨用户隔离
- 应用仍然具有现有 API 行为

### 阶段 3：重构 GraphQL 层

任务：

- 移除仅因为数据库未强制执行所有权而存在的授权逻辑
- 在必要时用守卫、过滤器和自定义变更替换分叉特定行为
- 减少敏感实体的通用生成变更
- 确保所有权字段是服务器派生的

退出标准：

- GraphQL 不再依赖分叉内部机制保证正确性
- 生成的 schema 对开发者生产力仍然可接受

### 阶段 4：移除分叉依赖

任务：

- 在可行的情况下，从分叉 Seaography 切换到上游兼容实现
- 将任何剩余的框架粘合代码隔离在本地应用抽象后面
- 移除死掉的兼容性代码

退出标准：

- 安全关键行为不再依赖 Seaography 分叉
- 分叉可以被归档或冻结

### 阶段 5：加固和简化

任务：

- 审计 GraphQL 外部的私有表暴露路径
- 为每个用户私有实体添加回归测试
- 在开发者文档中记录新的授权模型
- 简化 RLS 采用后变得冗余的解析器代码

退出标准：

- 授权模型可以在不阅读框架内部机制的情况下理解
- 未来贡献者可以安全地扩展系统

## 必需测试

### 数据库级别测试

这些是强制性的，因为正确性现在主要依赖于 RLS。

对于每个用户私有表，至少测试：

- 用户 A 可以选择自己的行
- 用户 A 不能选择用户 B 的行
- 用户 A 可以插入自己的行
- 用户 A 不能插入具有用户 B 所有权的行
- 用户 A 可以更新自己的行
- 用户 A 不能更新用户 B 的行
- 用户 A 不能将拥有的行更改为另一个用户
- 用户 A 可以删除自己的行
- 用户 A 不能删除用户 B 的行
- 未认证或缺失会话行为按设计被拒绝或为空

### API 级别测试

测试 GraphQL 行为保持正确和人机工程学：

- 未认证请求在预期的地方尽早失败
- 用户范围列表查询只返回自己的行
- 自定义变更不接受客户端控制的所有权字段
- 仅管理员操作保持受限

### 针对遗留行为的回归测试

在实际可行的情况下，在更改执行位置的同时保留预期的产品行为。

测试示例：

- 用户在 GraphQL 查询中仍然只能看到自己的订阅
- 下载任务操作保持在当前用户范围内
- 现有客户端流程不需要在负载中提供所有权字段

## 开发者和 AI 代理的实施规则

### 规则 1：不要重新引入安全关键的分叉修补

如果某个行为是安全关键的且当前在旧分叉中实现，将其移至：

- PostgreSQL RLS，或
- 明确的应用程序层代码

不要再次将其隐藏在修补的框架内部机制中。

### 规则 2：优先清晰而非巧妙

如有疑问：

- 添加明确的 `subscriber_id`
- 编写明确的策略
- 编写明确的自定义变更
- 拒绝模糊的所有权流程

### 规则 3：不要信任客户端提供的所有权字段

对于普通用户流程，所有权必须来自认证上下文，而非请求负载。

### 规则 4：生成 CRUD 必须逐个实体审查

不要仅仅因为 RLS 存在就假设生成的 GraphQL CRUD 是安全的。

审查以下方面：

- 变更表面在语义上是否合适
- 是否暴露了隐藏的内部字段
- 所有权相关字段是否可能被滥用或导致用户体验不佳

### 规则 5：保持 GraphQL 特定授权的浅层

GraphQL 逻辑应该易于在另一个框架中重写。

允许的形式：

- `require_auth(ctx)`
- `is_admin(ctx)`
- `entity_filter_for_current_user(ctx)`
- 自定义变更包装器

除非有令人信服的理由，否则避免构建深度框架耦合的策略 DSL。

### 规则 6：当所有权是间接的时，停下来重新设计

如果 AI 代理遇到一个只能通过多个连接间接派生所有权的表，它不得静默地即兴创作脆弱的授权快捷方式。

相反，它应该：

- 记录模糊性
- 建议添加明确的所有权列
- 添加迁移/回填计划
- 如有需要，标记该区域供人工审查

### 规则 7：安全正确性优先于代码生成纯粹性

可以接受在需要时减少自动生成的暴露或用自定义变更替换通用变更。

### 规则 8：保持可审计性

新授权行为必须可从以下来源发现：

- SQL 迁移和策略
- 记录的请求上下文设置
- 解析器/守卫/过滤器代码

审查者不应需要检查框架分叉来理解访问控制。

```text
  004-GRAPHQL-AUTH-GUIDE.md

src/

    context.rs
    guards.rs
    session.rs
  db/
    rls.rs
    transaction.rs
  graphql/
    filters.rs
    hooks.rs
    mutations/
      create_subscription.rs
      remove_subscription.rs
      pause_download_task.rs
```

重点是关注点分离，而非确切的文件名。

## 请求上下文模式

每个认证请求应产生一个包含至少以下内容的请求范围认证上下文：

- `subscriber_id`
- 认证状态
- 如需要，粗粒度角色信息

该上下文应注入到：

- 数据库执行路径，以便可以设置 `app.subscriber_id`
- GraphQL 上下文，以便守卫和过滤器可以读取它

重要约束：

- 在事务/请求范围而非全局池连接上设置 DB 会话变量
- 确保在任何用户范围查询之前应用设置
- 确保通过事务范围或等效机制自动清理

## 常见重构模式

### 模式 A：自动添加所有权约束的分叉钩子

旧方法：

- 自定义 Seaography 分叉将用户过滤器插入生成的查询路径

新方法：

- 用 RLS 强制执行行可见性
- 可选地在 GraphQL 过滤器中镜像相同范围以提高人机工程学

### 模式 B：生成的变更接受 `subscriber_id`

旧方法：

- 客户端负载可能指定所有权相关字段

新方法：

- 移除或包装通用变更
- 在服务器端从认证上下文派生 `subscriber_id`
- 让 RLS 作为第二道防线拒绝不一致的写入

### 模式 C：在框架内部机制中实现的管理员绕过逻辑

旧方法：

- 分叉特定的管理员分支深度存在于生成的堆栈中

新方法：

- 在守卫、过滤器或单独的解析器中明确表达管理员行为
- 如需要，使用精心设计的 DB 角色/会话策略，而非隐藏的绕过

## 风险和缓解

### 风险 1：RLS 意外破坏现有查询

原因：

- 缺少会话变量
- 策略不正确
- 运行时角色不匹配

缓解：

- 尽早引入 DB 级别集成测试
- 首先在开发环境中启用 RLS
- 在迁移期间记录请求认证上下文和事务设置

### 风险 2：池化连接泄露会话状态

原因：

- 跨池化连接错误使用会话级变量

缓解：

- 在事务范围使用 `SET LOCAL`
- 避免全局会话修改模式来处理每请求身份
- 仔细审查连接/事务生命周期

### 风险 3：所有权列缺失或不一致

原因：

- 遗留 schema 设计
- 历史数据模糊性

缓解：

- 将所有权规范化视为明确的迁移阶段
- 在依赖 RLS 之前回填和验证

### 风险 4：生成的 GraphQL 表面在语义上仍然太宽

原因：

- 代码生成暴露了在 RLS 下技术上安全但产品上不可取的变更

缓解：

- 逐个实体审查生成的操作
- 用自定义变更替换敏感的通用变更

### 风险 5：团队继续认为 GraphQL 过滤器是安全边界

原因：

- 来自框架分叉授权的旧心智模型

缓解：

- 记录 RLS 是事实来源
- 在 SQL 层而非仅 API 层添加测试覆盖
- 让审查者明确检查策略更改

## 验收标准

当以下全部为真时，迁移被视为成功。

### 安全性

- 每个用户私有表都受 RLS 保护
- 跨用户行泄露在数据库级别被阻止
- 运行时 DB 角色不会静默绕过 RLS

### 架构

- 安全关键授权不再依赖 Seaography 分叉
- GraphQL 授权逻辑是浅层且可替换的
- Seaography RBAC 不需要保证正确性

### 产品行为

- 用户仍然可以执行正常的订阅、任务和进度工作流
- 客户端不需要提交所有权字段
- 未授权访问安全且可预测地失败

### 可维护性

- 开发者可以从文档、迁移和普通源代码理解访问控制
- AI 代理可以在不修改框架内部机制的情况下扩展系统
- 未来从 Seaography 迁移仍然是可行的
